# seanime-account

Account and sync server for Seanime Mobile, a Cloudflare Worker (`seanime-account`).

The server is an encrypted mailbox. Devices encrypt everything before upload. The server never gets plaintext, a password or the data key (DEK), unless the owner turns on "sign in with an email code only" (below), which hands it a sealed copy of the DEK. For email login it stores only `HMAC-SHA256(pepper, authKey)`, where `authKey` is derived on the device from the password with Argon2id, and compares it in constant time.

The server is not trusted with keys either. It cannot add a device that the devices accept, hand out a key they accept, or lower the Argon2 parameters: devices check all of that themselves (see "Key trust" below). What the server can still do is refuse service or hand out stale data, which the devices notice.

Storage: D1 (`DB`) for accounts, sessions, devices and wrapped keys; R2 (`SNAPSHOTS`) for one encrypted blob per account at `snap/<userId>`.

Events older than 180 days are removed by the cron. |

| DELETE | `account/web-access` | Edit on the website off, any session (the website too). Every website key session of the account is locked in the same step. `204`; mail and event `web_edit_off` when it was on. |
| POST | `web/unlock` | Website only (cookie session from `ALLOWED_ORIGIN`, else `403 website_only`). `403 web_edit_off` before anything is counted. Answer `{userId, dekId, kdf, method}` plus `wrappedDek`, `recoveryWrappedDek` or `escrowDek`. `409 no_key` without a key, `409 rewrap_needed` when the password wrap is gone. A Google account without a password unlocks with the recovery code only. Ends a key proof from before. Mail and event `web_unlocked` (with the method) on every successful unlock, since the wrap leaves the server here, whether or not `web/key` follows. |
| POST | `web/key` | Website only, within 5 min after `web/unlock` of the same session, once (also when it fails; else `403 unlock_required`). `{dekId, dekProof}`: `409 dek_mismatch` for another key, `403 key_required` for a wrong proof. Answer `{dekId, keyUntil}`: the session reads and writes the snapshot for 30 minutes (`keyUntil`), while Edit on the website stays on and the account keeps that dekId. No mail or event of its own (`web/unlock` sent them). |
| POST | `web/lock` | Any session, `204`: ends this session's unlock and key proof at once. Signing out ends them too. |
| PUT | `account/escrow` | "Code only" on: `{dek, dekProof, authKey}` from a device session (`device_required` otherwise), never from a website session (`403 app_required`). The password again, checked and counted like Disconnect Google (`403 wrong_password`). `dekProof` of the key sent must be the account's (`409 dek_mismatch`), so a device with an older key never seals that one. The DEK is sealed with AES-GCM under `ESCROW_KEY`, AAD `sm-escrow-v1\n{userId}\n{dekId}`. `204`, mail and event `code_only_on`. |
| DELETE | `account/escrow` | "Code only" off, any session. The sealed copy is deleted at once. `204`, mail and event `code_only_off` when one was there. |
| POST | `account/password/after-code` | `{authKey, salt, kdf, wrappedDek, dekId, dekProof?}`. Only a code session within 15 min of its sign-in (else `403 reauth_required`), only for an account with a password (else `409 no_password`), `dekId` must be the account's (else `409 dek_mismatch`), and a session without a device row needs the DEK proof (`403 key_required`). New password and wrap, `rewrapNeeded` cleared, a linked Google sign-in removed, other sessions stay. Mail `password_changed`. |
| PUT | `account/keys` | `{dekId, dekProof?, wrappedDek?, recoveryWrappedDek?, recoveryProof?, device?}`, sign-in within 10 min. The first DEK of an account needs `device` and `dekProof`. After that a session bound to a device row may write; a session without one needs the DEK proof AND the owner (S3): a password sign-in, the `recoveryProof` (its SHA-256 is stored with every new recovery wrap), or its own live row (same device key, same signing key, not signed out). The DEK proof alone never adds a row. Another session's row is never overwritten. Mail and event for a new device and for a new recovery wrap. |
| GET | `account/keys/device` | `{deviceId, dekId, sealedDek, chainFrom, chainMac, rotatorPub, removed}` of the session's device. After another device rotated, this device picks up its new key here and takes it only if the box opens with `rotatorPub`, that device is not on its removed list and `chainMac` (chain v2) checks out. |
| POST | `account/start-fresh` | `{dekId, dekProof, wrappedDek?, recoveryWrappedDek?, device}`. Sign-in within 10 min, by the password or (4.2.0) a code. One transaction: snapshot, every device, open approvals, the "code only" copy and all other sessions go, Edit on the website goes off (also the key session of this one); the new dekId, its wraps and this device are set. A code session may leave out `wrappedDek` of a password account: then `rewrapNeeded` is set and `account/password/after-code` sets the password. Then the R2 blob is deleted and a warning mail goes out. Wait (4.2.x): within 24 hours after a password reset (any session, also the password sign-in after it) and, for a code session, within 24 hours after the first code sign-in of the 7-day window with the session's own signing key (`code_anchors`, per account and `sig_pub` of the device or browser; later codes with that key in the window don't move it, a key without such a sign-in waits the full 24 hours), `403 start_fresh_wait` with `retryAfter` (seconds) and nothing changes. An owner's code with another key never shortens the wait of a new key, so a mailbox holder's brand-new key always waits a day. The daily cleanup removes anchors older than 7 days. A password sign-in without a recent reset and a Google sign-in never wait. Whoever holds only the mailbox can't wipe the data at once, and the owner has a day to see the sign-in in the timeline. |
| POST | `account/password` | Sign-in within the last 10 min and the DEK proof required. Signs out other sessions. Mail. |
| POST | `account/rotate` | "Change encryption key", `multipart/form-data` with parts `meta` (JSON: `oldDekId`, `dekId`, `dekProof`, `chainMac`, `devices[{deviceId, sealedDek, mac}]`, `removed`, optional wraps and `recoveryProof`, and `escrowDek` (the new raw DEK) which is required while "code only" is on, else `409 escrow_required`) and `snapshot`, `If-Match` required. Any device session, sign-in within 10 min. S2: `devices` is an allowlist, the rows the user kept (live, the rotating device among them); every other row is removed in the same transaction and must be named in `removed`, which the chain carries. Afterwards wraps of the old dekId are refused. Without a new recovery wrap the old one and its proof are dropped and `recoveryRenewalNeeded` is set. If writing R2 fails, the key rows are put back (left-out devices stay removed). Mail and event per removed device and for the key change. |
| POST | `account/link-google` | `{idToken, nonce, authKey}`. The password again (counted like a login). Mail. |
| POST | `account/unlink-google` | `{authKey}`. "Disconnect Google" for password accounts, the password again. Mail. |
| DELETE | `account` | Sign-in within the last 10 min required: a password account needs the password (typed again or a password sign-in), a Google-only account its Google sign-in, never a code. Removes D1 rows (also open sign-in codes and the "code only" copy) and the R2 blob at once. |
| GET | `sync/meta` | Also `rotationRequired`, `rewrapNeeded`, `recoveryRenewalNeeded` and `removedDevices` (device keys removed from the account; the devices remember them). |
| GET/PUT | `sync/snapshot` | Only for a key holder: an app session bound to a device row (`403 device_required` otherwise), or a website session after `web/key` (Edit on the website on, else `403 web_edit_off`; proof within 30 min and for the account's current dekId, else `403 unlock_required`; from `ALLOWED_ORIGIN`, else `403 website_only`). A website session never counts as a device, also when bound to a device row. PUT needs `If-Match: <version>` (`409 version_conflict` with `{version}`), `X-Dek-Id` (`409 dek_mismatch`) and `Content-Length`, body `application/octet-stream`, 1 byte to 10 MB. The website never writes the first package nor one after `DELETE sync` (size 0): `409 no_snapshot`. The first save of a website key session adds the event `web_settings_changed` (no mail). |
| DELETE | `sync` | Deletes the stored package. The version counts on and stays (`sync/meta` then says `size: 0`, `dekId: null`), so no device sees an older version; the next upload builds on it. |

Sessions: 256-bit random token, only its SHA-256 is stored, 90 days idle timeout. A session in use writes its `last_used_at`, the account's `last_active_at` and, when it is bound to a device row, that device's `last_seen_at` (`GET devices`), at most every 5 minutes. The app sends `Authorization: Bearer <token>`. Requests from `https://seanimemobile.com` get the `__Host-sid` cookie instead. Every other `Origin` is rejected.

### Signed requests (plan 10.2b, `src/signature.ts`)

Every session is bound to a signing key whose private half never leaves the device: the app uses an ECDSA P-256 key made inside the Android Keystore (StrongBox when the phone has one, else the TEE; not exportable; `native/modules/core-sodium`), and only on a phone without Keystore Ed25519 from libsodium in expo-secure-store. The website uses a non-extractable WebCrypto key in IndexedDB (Ed25519 when the browser has it, otherwise ECDSA P-256 with SHA-256). The app keeps its key across sign-ins of the account and deletes it when the user signs out; the website deletes its key at sign-out too. The session row stores `sig_alg` (`ed25519` or `p256`) and `sig_pub` (raw public key, base64url: 32 bytes, or the 65-byte uncompressed P-256 point). The token alone is not enough for any endpoint.

Every request with a session carries three headers:

| Header | Value |
| --- | --- |
| `X-SM-Sig` | base64url signature, 64 bytes (Ed25519, or ECDSA P-256 as `r \|\| s`, 32 bytes each; the phone unpacks the Keystore's DER signature into this form) |
| `X-SM-Ts` | unix time in milliseconds, 13 digits |
| `X-SM-Nonce` | 16 random bytes, base64url (22 characters) |

The signature covers the UTF-8 bytes of

```
v1\n{METHOD}\n{path+query}\n{hex SHA-256 of the raw body}\n{X-SM-Ts}\n{X-SM-Nonce}\n{session id}
```

`path+query` as sent (`/v1/sync/snapshot`), the body hash over the exact bytes (an empty body hashes the empty string). The session id is `base64url(SHA-256(token))` when the token goes as Bearer (the app), and `-` for the website's HttpOnly cookie (the page cannot read it) and for sign-ins. The server checks the signature against the session's key, the time within 5 minutes of its clock and the nonce (once ever; table `used_nonces`, cleaned by the daily cron). Missing or wrong: `401 unauthorized`, the same answer for every cause.

Sign-in: `auth/prelogin` answers a one-time `challenge` (36 bytes base64url: time, random, HMAC bound to the email; unknown emails get one made the same way). `auth/google/nonce` answers one bound to the nonce. `auth/login`, `auth/signup` and `auth/google` must carry `challenge` and the new key `sigKey: {alg, pub}` in the body and be signed with that key (session id `-`). A challenge works for 5 minutes and once, so a captured sign-in cannot be sent again. The new session is bound to `sigKey`.

Order of checks (N-2): the route's size limit comes first, from `Content-Length`, before a byte is read: 16 KB on every route except `PUT sync/snapshot` (10 MB) and `POST account/rotate` (10 MB plus meta). On those two the session must exist, the signature headers must have the right form and the account's upload counter (30 per hour) is counted before the body is read; a website session counts on its own counter first, on both routes. Then the body is read once, hashed and the signature checked.

### Key trust (`native/src/core/account`)

- `dekProof` = `KDF(DEK, 2, "sm-dkey")`; the server stores its SHA-256. Only a session that shows it, or one bound to a device row, can change wraps, add a device or start over.
- Every device row carries `mac`, a keyed BLAKE2b under a key derived from the DEK over `userId || dekId || devicePub`. Devices list and seal only to rows whose MAC checks out and show the others as unverified.
- Wraps and boxed keys carry their `dekId` in the AAD or the boxed plaintext, so an old key cannot be served under a new id. Keys go from device to device only as `crypto_box` (the receiver checks the sender's key), never as an anonymous sealed box.
- Key chain v2: a rotation stores `chainFrom` (the old dekId), the rotating device's key and the removed device keys, and `chainMac` (the old DEK's MAC over all of them and the new DEK). A device takes a new key from `account/keys/device` only with a matching chain, a box from that device and a rotating device it does not know as removed.
- Approval v2: `commitment = SHA-256("sm-commit-v2\n" || pkN || rN)`, number = 6 digits of `SHA-256("sm-approve-v2\n" || pkN || pkO || rN || rO)`; both devices ask whether the other one shows the same number before they approve or take the key. One number per request: "No", a timeout or a swapped value end it for good (S1).
- Key change (S2): only the devices the user keeps get the new DEK; the server removes every other row in the same step. The app never changes the key on its own.
- Owner (S3): `recoveryProof` = `KDF(recoveryKey, 1, "sm-rcvr")`, the server keeps its SHA-256. A password sign-in or this proof lets a device join; the DEK proof alone never does. Invariants I1 to I5: `docs/SECURITY-AUDIT.md`, round 4.
- KDF floor: the app and the website refuse Argon2id below `m = 65536, t = 3` and below what they saw for the email before.

Sign in with a code (4.2.0, `src/codelogin.ts`): a code proves the mailbox, not the password. By default the session gets no key and the device unlocks like any new one (approval, recovery code) or starts fresh. A code session counts as the owner (S3) only for Start fresh (the mailbox could reach it through a reset anyway) and, when "code only" is on, for joining with the key through `PUT account/keys` (mail "New device"). It never deletes an account, removes a device only with "code only" on, and never changes the password except through `after-code` within 15 minutes. An account without a password (Google only) gets no code at all, and a code session never owns one. "Code only" is opt-in and off by default: then the server holds a copy of the DEK sealed under `ESCROW_KEY` and can read the synced data; turning it off, Start fresh and deleting the account remove the copy, a key change replaces it.

Edit on the website (4.2.x, `src/websync.ts`): opt-in and off by default, set only by the app (`users.web_edit`). Without it no website session gets the snapshot, whatever the page's code does. With it the website shows the owner (`web/unlock`: password, recovery proof, or a code with "code only"), unwraps the DEK in the browser and shows the DEK proof (`web/key`); the DEK proof alone never unlocks (I3). The proof is kept per session (`sessions.key_proof_at`, `key_dek_id`) for 30 minutes and ends with a key change, `web/lock`, sign-out and turning the opt-in off. The page locks itself earlier (5 minutes without input). Every unlock is mailed. The server still never gets the DEK from this; the browser holds it in memory while unlocked.

Device approval (plan 6.4): request -> `rO` from an old device -> `rN` revealed by the new device -> approve/deny. Out-of-order steps answer 409, a wrong commitment ends the request (422). Requests expire after 10 min; at most 3 open and 5 new per hour per session, so one sign-in can't use up the owner's (NEU4-4). Byte format: `commitment = SHA-256("sm-commit-v2\n" || devicePub[32] || rN[32])`, all values base64url without padding (see `src/approval.ts`).

Mail goes through the Cloudflare Email Service binding `EMAIL` from `no-reply@seanimemobile.com`: confirm email, password reset, new device, removed device, password changed (a linked Google sign-in is removed with it), start fresh, account deleted, Google linked, Google disconnected, recovery code changed, key rotated, inactivity warning, sign-in code, code only turned on, code only turned off, Edit on the website turned on, turned off, synced data unlocked on the website. Links carry the token in the URL fragment. In tests the binding is replaced by `test/mail-sink.js`, which records mails.

Rate limits:

- Login (and the password asked again for Google link/unlink): first 20 per IP (IPv6 per /48), counted before the sign-in's nonce and challenge are written; then 5 attempts per (email, IP range), with a growing wait (30 s doubling up to 15 min) that only holds up that network. IP range = IPv4 /24, IPv6 /48. Every attempt is counted in one statement before the password is checked (`INSERT ... ON CONFLICT DO UPDATE ... WHERE <not waiting> RETURNING`), so parallel attempts cannot pass the limit.
- Across all networks 20 per email within 15 min: over that nobody waits; a right and a wrong password get the same `202 {confirm: "email"}`, and only the right one mails a sign-in link (S5). After the owner pressed the button on the link's page, the same signing key with the right password signs in once within 15 minutes; a wrong password from that key still counts and gets 202 (NEU4-2). Under the counter a guesser gets real 401s per network, over it the same 202 for every answer.
- A known device skips the email counters: when the login is signed with the key stored on one of the account's live device rows (not signed out), only the IP counter applies.
- Sign-in codes: 3 requests per hour per (email, IP address, IPv6 /48), mails in their own pot `code` like reset links; 5 tries per code; `auth/code/login` also counts the login counter per IP (20) like `auth/login`. Code tries (counted before the check, 429 over the cap): from a network the account signed in from with its password or a code (remembered 90 days, NEU4-1) 20 per (email, IP range) a day; from every other network 20 per email a day and 50 a week across those networks. So strangers elsewhere never hold up the owner's network (I4), and guessing stays at about 2600 tries a year (0.26 % to hit one code). Code mails from a known network skip the cap across networks the same way.
- Edit on the website, per account and hour: 10 uploads from website sessions (snapshot and rotate), counted on their own counter before the account's upload counter (so the website never uses more than 10 of the devices' 30); 60 snapshot reads by website sessions; 5 unlocks with the recovery proof. A password unlock counts like a sign-in, a code unlock like a code sign-in.
- Signup 5 per hour per IP; upload 30 per hour per account; reset 3 per hour per (email, IP address, IPv6 /48); verification resend 3 per hour per account; device approvals 5 per hour per session, paused for an hour after three "No" from devices of the account (mail; a session without the key never counts). Reset, confirmation and sign-in link mails at most 5 per hour and 10 per day per (recipient, sender network), and 50 per day per recipient across networks, each kind in its own pot (NEU4-1): only the right password fills the sign-in link pot, and a reset from a network the account signed in from with its password (kept 90 days as a keyed hash) counts per address instead (5 per hour, 10 per day) with 50 per day for the whole network instead of the cap across networks, so a stranger in the same network uses up only his own (NEU5-1). A password sign-in within the last 10 minutes skips the email counter when the password is typed again (delete account, disconnect Google); an older one is asked to sign in again (NEU5-2).
- Short bursts per IP (IPv6 per /48) go through the Workers Rate Limiting bindings, in memory, before any route without a session writes to D1. The Google nonce is stateless and the sign-in challenge is checked before its use is written. Counter keys are HMACs, no raw IP or email is stored.

Logs (`wrangler.jsonc` `observability`): invocation logs and traces are off, query strings are redacted. The Worker writes one line for an unexpected error (route and error type) and one for a failed mail (kind and code), a failed sign-in code or a code-only copy that does not open (only that), never a body, token, email or IP. Cloudflare keeps these lines for a few days.

A daily cron removes expired tokens, sign-in codes (also used up ones), device requests, nonces, counters and idle sessions, and deletes accounts that are still unconfirmed after 7 days (checked again inside the delete transaction). After 180 days without activity it sends a warning; an account still unused 14 days after the warning is deleted (D1 and R2) with a mail.

## Local commands

```sh
npm install
npm run typecheck     # tsc --noEmit
npm test              # vitest with local D1/R2 (Workers runtime)
npm run types         # regenerate worker-configuration.d.ts after changing wrangler.jsonc
cp .dev.vars.example .dev.vars && npm run migrate:local && npm run dev
```

The test run prints a warning about missing secrets; the test config injects fixed test values.

## Secrets

Set with `wrangler secret put`, never committed:

- `PEPPER_V1`: HMAC pepper for stored auth hashes
- `ENUM_SECRET`: key for decoy salts and rate-limit counter keys
- `GOOGLE_WEB_CLIENT_ID`: Google OAuth web client ID, the expected `aud` of ID tokens
- `ESCROW_KEY`: 32 random bytes, base64url (required); seals the DEK of accounts with "code only" on. Losing it turns those copies off in effect (`escrowDek` comes back `null`), changing it needs every copy to be sealed again.

Vars in `wrangler.jsonc`: `ALLOWED_ORIGIN`, `WEB_BASE_URL` (links in mails), `GOOGLE_JWKS_URL` (Google's key set; another URL is taken only for a test host, `*.test` or localhost). ID tokens with several audiences need `azp` naming the client. Binding `EMAIL` (`send_email`, sender restricted to `no-reply@seanimemobile.com`); the domain must be onboarded to Email Sending before the first deploy.

The D1 `database_id` and rate-limit `namespace_id` values in `wrangler.jsonc` are placeholders.
